# Main process

Electron's main process: the only place that builds the adapters, holds paths, and does anything privileged.

`index.ts` is bootstrap only — it builds the shared `MainContext`, verifies the toolchain, clears what a run that was killed left behind (a half-made first book in the pending folder and old scratch folders in the temporary one, both only after a day), registers every IPC handler group, opens the window, and cleans up (tools, sharing, pending settings writes) before quitting. The actual work is split by responsibility:

- **`context.ts`** — the `MainContext` type (everything the handlers share: selection maps, the active job/sharing state, the constructed workflow) and `createMainContext()`. A handler-registration function is typed to receive only the `Pick<MainContext, ...>` slice it actually touches, so its real dependencies are visible and checked at its call site.
- **`constants.ts`** — fixed configuration values, such as the OPDS port.
- **`toolchain-bootstrap.ts`** — verifies the bundled tools and, only if they match the lock, builds the workflow around the mangabind and mangapress adapters onto the context.
- **`window.ts`** — opens the window with the sandbox on, context isolation on, Node integration off, and navigation denied, and refuses every permission request but the clipboard write (`permission-policy.ts`). It is painted, and its title-bar buttons drawn, in the colors of the theme that was chosen (`themeWindowColors` in `domain/theme.ts`), `applyThemeToWindow` gives an open window those of a theme that is kept later, and `applyThemeToApp` gives what the system draws (dialogs, menus, scrollbars) its scheme (ADR 0066, ADR 0067).
- **`app-protocol.ts`** and **`renderer-files.ts`** — the packaged page is served from the `app://mangabound` scheme, not `file://`; the page itself is given with the `data-theme` of its `<html>` already set to the chosen theme (`pageInTheme`), so the first paint is never in the other one (ADR 0067). `renderer-files.ts` decides, without Electron, where the page is and which file a request names (nothing outside the renderer folder); `app-protocol.ts` registers the scheme and answers from disk. `renderer-files.ts`, `app-protocol.ts` (with Electron's `protocol` replaced) and `permission-policy.ts` have unit tests under the 100% gate. See [ADR 0041](../../docs/adr/0041-the-window-loads-its-page-from-its-own-scheme.md).
- **`leaving.ts`** — asks before the app is left while a conversion runs (ADR 0059): one guard shared by the window's close (not on macOS) and `before-quit`, a native box with the safe answer as the default, and what counts as running is a queue that the window has begun (`queue-runs.ts`) or a conversion that `ipc/run-job.ts` keeps (ADR 0065), not every job. Under the 100% gate.
- **`queue-runs.ts`**, **`keep-awake.ts`**, **`queue-notice.ts`** and **`ipc/queue-runs.ts`** — a queue is one press of Process, and the window says when it begins and ends (`queue:begin`, `queue:end`; ADR 0065). `QueueRuns` keeps the queues, each belonging to the window that began it, with the choices it began with; the page going away lets go of its queues, and so does the quit. Three things follow the count: the guard above asks while a queue runs, `KeepAwake` holds one `powerSaveBlocker` while a queue that asked for it runs, and `announceQueueEnd` shows a system notification when a queue longer than 30 seconds ends with no window in front (the rule is `domain/queue-run.ts`; the words are `dialogs.queueEnded`). The Electron parts (blocker, notifications, windows) are handed in, so each is tried without Electron. Under the 100% gate.
- **`conversion-limit.ts`** — how many books of a title the workflow converts at once, as a function it is asked each time a title starts (ADR 0068): what the queue that is running began with (the fewest if several run), or what is chosen now when none does, worked out from the computer each time. `toolchain-bootstrap.ts` gives it the registry, the app settings and the machine. Under the 100% gate.
- **`log.ts`** — makes `console.error` and `console.warn` write to the log file (`adapters/log/file-log.ts`) as well as the terminal, writes an uncaught exception as it ends the app (a monitor, not a handler, so the app still stops), and says where the log folder is. It is made first when the app is ready and waited for last when it quits. Under the 100% gate (ADR 0058).
- **`window-state.ts`** — keeps the size and place of the window between sessions (ADR 0062): reads `window-state.json` once, tells `window.ts` where to open, and follows the window (a state that has stayed half a second, the close, and the quit); a Wayland session keeps no place. Under the 100% gate.
- **`diagnostics.ts`** and **`ipc/troubleshooting.ts`** — what helps a report of a problem (ADR 0057): the diagnostics text, built here and put on the clipboard, with no path, name or log in it (a test looks for them), and the folders of the app (its data, and the log) opened in the file manager by name. Under the 100% gate.
- **`ipc/processing-folder.ts`** and **`processing-status.ts`** — where the app works (ADR 0056): three commands (read it, choose a folder, go back to the app's own places). The dialog is opened here and the folder is checked before it is kept; a change is refused while a conversion or a share is running, and again if one started while the dialog was open. A fourth command, `app:get-working-space`, says what is left on the drives of both places and whether they are one (ADR 0060). The status also adds up what waits (`waiting-books.ts`), and `ipc/pending-cleanup.ts` counts and deletes the conversions untouched for 7, 30 or 90 days, under the rules of deleting one conversion (ADR 0061). `processing-status.ts` says what the window is shown and lets go of earlier folders that are there and empty. `index.ts` reads the app settings first, since where the app works depends on them. Under the 100% gate.
- **`ipc/updates.ts`** — the one command that looks for a newer version (ADR 0063): it asks with the version that is running, which only this process knows, and answers with what the check found or with the failure of an online source. Nothing calls it but the button of the Updates tab.
- **`project-links.ts`** and **`ipc/project-links.ts`** — the addresses the About tab can open (always https, the guide's by language) and the one handler that opens them in the system browser: the window names a place and never gives an address (ADR 0054). Under the 100% gate; a test also says when the support address differs between the app, the website and `.github/FUNDING.yml`.
- **`ipc/*.ts`** — one file per handler group (inputs, conversion, pending books, metadata, artifacts, OPDS, settings, the app's own settings, and the links of the About tab). Every group uses `ipc/handle.ts` to validate its payload with the schema from `src/shared` before running, catch errors and return a `WorkflowResult`. Commands with no payload retain their ignored-argument behavior. Command-specific error mapping remains explicit: pending recovery/deletion/save messages and sharing-state cleanup are not replaced with a generic failure. Selections, sessions, pending runs and books are opaque ids resolved here. Native Save dialogs run here; the page never supplies an export path. The titles of the native dialogs are written here, in the language the window is in (`ipc/dialog-words.ts`).
- **Decisions pulled out of the handlers,** each a small unit with its dependencies handed in and a unit test under the 100% gate, so that a refactor cannot loosen one with CI staying green: `ipc/pending-decisions.ts` (which books Save All may take, when a pending run may be deleted, which extension a book may be saved with), `ipc/selections.ts` (a selection id can be used once), `ipc/artifact-access.ts` (a saved book is opened only while it is still a file), `ipc/remembered-folders.ts` and `ipc/preferences-state.ts` (what is remembered of the dialogs' folders and the options, and what is written down with them), and `quit-cleanup.ts` (what is let go of when the app quits, in the order that keeps a person's work). The handlers that call them keep only the wiring.
- **`ipc/run-job.ts`** — the shared lifetime for single-input and library conversions: resolve pending storage, refuse a deleting run or duplicate job id, register cancellation, track completed artifacts, and finish ordered catalog publication before removing the active job. Earlier books remain tracked when a conversion fails; a catalog error is logged without stopping later publications. Progress and request/result translation stay in `ipc/conversion.ts`.
- **`ipc/result.ts`** — `ok`, `failed` and `toFailure`, which turns whatever a handler caught into what the page is told. What it tells the page is a code the window writes in its language (`said`, ADR 0053), never a sentence. An error written for the screen keeps its message; the others get a short one that says what to do, and the error itself goes to the log with `console.error` (on the terminal, and in the log file, `log.ts`, ADR 0058). Something that only makes sense for one handler is mapped by that handler first: `ipc/sharing-failure.ts` for the errors of starting the sharing server, because the same system error codes mean something else from a file operation.

This layer stays thin: conversion behavior belongs in the application and adapters; save-name retries and typed save-error messages belong in `src/library/pending-save.ts`, which reuses `uniqueFileName`. `handle.ts` and `run-job.ts` have focused unit tests and are explicitly included in the 100% gate. The registration helper's tests replace only Electron's registrar; job tests need no Electron runtime. Error mapping still has unit tests (`tests/unit/to-failure.test.ts`). Real handler registration, dialogs, bridge validation, recovery, exclusive exports and conversion wiring are checked by packaged end-to-end tests. Every file of `src/main` is under the 100% gate (`src/main/**`), the window, the scheme and start-up included, with Electron replaced by a fake; what a fake cannot show (a real window, a real dialog) is what the packaged end-to-end tests are for.
